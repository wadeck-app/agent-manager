# Threat Model -- Agent Fleet Manager

**Version:** 1.1
**Date:** 2026-11-14
**Methodology:** STRIDE

## Scope

Hook-fed CLI, local daemon, web UI, and the reply channel that injects user text into running agents. app-core runs locally only (user fact, decision 11).

## Assets

| Asset | Sensitivity | Owner |
|---|---|---|
| Agent transcripts (code, secrets in tool output) | High | User |
| Reply channel (text injected into agents that run with the user's rights) | High | User |
| Session `.key` peer tokens read by the daemon | High | User |
| Uploaded images and audit log (kept 90 days, unmasked) | Medium | User |
| Permission bypasses (v2) | High | User |
| Owned sessions (daemon children that run tools with the user's rights) | High | User |

## Threat actors

| Actor | Motivation | Capability |
|---|---|---|
| Other local process/user | Read logs, inject replies | Reach localhost ports |
| An agent (any session) | Prompt-injected or misbehaving; reach another session | Bash tool: `curl` to the loopback reply route (R-03) |
| Malicious web page | CSRF / DNS rebinding to localhost daemon | Browser requests to localhost |
| Attacker-influenced transcript content | XSS or crafted links in the viewer | Text rendered by the UI (R-07) |

## STRIDE analysis

### Spoofing
Unauthenticated localhost UI/daemon could be driven by any local process, any agent via curl, or a web page. Mitigations: T-01, T-06, T-08.

### Tampering
Reply injection (T-07, T-08), uploads (T-05), the private socket protocol (T-04) and (v2) bypass grants change what agents do.

### Repudiation
Every web reply is recorded in the audit log (session, time, text, transport, outcome) shown in the UI (decision 11); the origin marker (setting `replyMarker`, default none since D-2026-11-19-a) names the origin in the transcript only when it is not none. Audit files are append-only by convention, not tamper-proof against a same-user process (accepted, local single-user).

### Information Disclosure
Transcripts may contain secrets; the UI exposes them (T-03). Audit text and uploads persist 90 days unmasked (T-11).

### Denial of Service
Hooks run in the agent's process path: a slow or hung hook CLI would block the agent, and hook volume is high (T-02).

### Elevation of Privilege
Reply channel and v2 bypass UI are privilege-bearing (T-01, T-08, T-10).

| T-12 | Spoofing/EoP | A local process (or an agent through Bash) that holds the daemon token launches claude sessions, sends them messages, switches their permission mode or approves their tool calls: a keyboard plus an approval button | Daemon bearer token on every route (`health_token`, constant-time compare, never in a response, log, event or audit); sessions API on 127.0.0.1 only, Host must be loopback with the API port (DNS rebinding), ANY request with an `Origin` header refused (only server-side callers use the API: the app-core module backend and the CLI send none; "not for browsers"), `Sec-Fetch-Site: cross-site` refused, token never accepted in the URL; strict body validation (1 MiB, JSON only, unknown fields refused, absolute existing cwd, model and mode checked so a value cannot become a flag, images by magic bytes, 700 KiB); at most 10 live children; the SSE stream carries ids, states, counts, tool name, display name, the permission description (cut to 300 characters) and the blocked path, never message text, tool input, stderr, protocol error details or a token (full tool input only on `GET /sessions/:id/permissions`, stderr tail only on `GET /sessions/:id`); the audit (`audit/owned-<day>.ndjson`) records launch, resume, send (counts only), interrupt, mode, permission decision (tool name only), stop, forget, shutdown, never text, tool input or token; allow is once (suggestions never echoed); children are ended only by the daemon that started them, leftovers after a crash are listed, never killed; the module routes that reach the daemon (launch, resume, stop, interrupt, mode, permission decision, reply) need the PIN (T-01) | Implemented (Phase 2). | T-14 | Info disclosure | A page or process that reaches the loopback app-core enumerates the directories of the machine through the folder picker (`GET /folders/list`, `/search`, `/recent`, `/roots`; no PIN, unauthenticated like every GET) | Names of folders only (never a file or a content), only inside ALLOWED ROOTS: the folders of `launchRoots` in config.yml (`agent-manager launch-roots add\|remove\|show`) plus the PARENT of the cwd of every session and launch (a cwd directly under a drive root or the home folder contributes itself, never that parent; a cwd that is the home folder or a drive root contributes nothing; the home folder, `C:\Users` and drive roots are never default roots). The name is checked against the roots BEFORE the disk is touched (a path outside never reveals whether it exists), then the real path (links and junctions resolved) must still be inside a root: a link in a root that leads out is not listed and not followed. `..` segments, relative paths, control characters and UNC paths (`\host\share`: contacting another machine, credential leak) are refused; hidden (dot) and technical folders are not listed; at most 300 entries per listing and 5000 directory entries read, 4000 folders scanned per search (cache 30 s). A cwd that equals or contains the home folder, is a folder of accounts (`C:\Users`, `/home`, `/Users`) or is another account's home never becomes a root. The scope is reused for 4 s while config.yml, the registry folder and the daemon list look the same.
